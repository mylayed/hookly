# Ядро аналізу Hookly

Усе ядро лежить у `src/lib/analyzer/`. Інтерфейс на Next.js (тиждень 3) імпортує його з `@/lib/analyzer`.

## Як працює аналіз

1. **Сегментація** (`segment.ts`): сценарій розбивається на «біти» (одне речення на біт), кожен отримує таймкод за темпом озвучки (2.3 / 2.7 / 3.2 слова на секунду). Текст у `[дужках]` і `(дужках)` вважається режисерською приміткою і не озвучується.
2. **Оцінка** (`analyzeScript`, Sonnet 5): модель за рубрикою ставить **1–5** за кожен із 5 критеріїв. Спершу вона цитує докази зі сценарію, потім порівнює їх з еталонами рівнів 1/3/5 і тільки після цього ставить бал. Відповідь приходить у строгому JSON через structured outputs.
3. **Загальний бал 0–100 рахує код** (`scoring.ts`), а не модель: це зважена сума критеріїв (хук 30%, утримання 25%, решта по 15%). Якщо хук оцінено на 1–2, загальний бал не може бути вищим за 60.
4. **Карта ризику**: по одному запису на кожен біт з рівнем low/medium/high, типом проблеми, причиною і конкретною правкою.
5. **Хуки** (`generateHooks`, Sonnet 5): 5 варіантів, кожен іншого типу. Вони не можуть обіцяти те, чого немає в сценарії.
6. **Переписування** (`rewriteWeakSpots`, Opus 5): змінюються тільки жовті й червоні біти, стиль автора зберігається. Нові факти модель не додає: якщо для правки бракує інформації, вона ставить `[placeholder]`.

Рубрика (`rubric.ts`) є головним активом продукту. Її варто покращувати першою.

## Налаштування

```bash
cp env.example .env.local   # і встав ANTHROPIC_API_KEY та ключі Supabase
npm install
```

Supabase (одноразово):

1. Створіть проєкт на supabase.com. У **Project Settings → API Keys** візьміть URL, publishable key і secret key → `.env.local`.
2. **SQL Editor** → виконайте `supabase/migrations/20260926000000_history_and_limits.sql`.
3. **Authentication → Sign In / Providers** → увімкніть **Allow anonymous sign-ins**.
4. **Authentication → URL Configuration**: Site URL `http://localhost:3000` (на проді домен), у Redirect URLs додайте `http://localhost:3000/auth/callback` (і такий самий для продового домену). Без цього Supabase ігнорує повернення на `/auth/callback`, і вхід не завершиться.
5. **Google:** у Google Cloud Console створіть OAuth client (Web application) з redirect URI `https://<ref>.supabase.co/auth/v1/callback`, потім у Supabase **Sign In / Providers → Google** вставте Client ID і Client Secret.
6. **Пошта:** вбудований SMTP Supabase надсилає лише кілька листів на годину і тільки на адреси учасників проєкту. Для справжніх користувачів підключіть власний SMTP (**Authentication → Emails → SMTP Settings**, напр. Resend).

## Мови

Інтерфейс і фідбек: English, Українська, Español, Português (BR), Français, Deutsch, Polski (`src/lib/i18n/`).

- Словники лежать у `src/lib/i18n/dictionaries/`. `en.ts` задає тип `Messages`, тому TypeScript не дасть пропустити ключ в іншій мові. Множина рахується через `Intl.PluralRules` (`plural.ts`): 1 рядок / 2 рядки / 5 рядків.
- Вибір мови зберігається в cookie `hookcheck-locale`, тому сервер одразу рендерить потрібну мову, `<html lang>` і `<title>`. При першому візиті мова береться з `Accept-Language`.
- API приймає `locale`. Фідбек (оцінки, причини, правки, пояснення хуків, нотатки переписування) модель пише мовою інтерфейсу й звертається до автора так, як задано в `LOCALE_INFO.address`. Сам сценарій, хуки й переписані рядки лишаються мовою сценарію, яка може бути будь-якою.
- Помилки API повертають `code` і `params`, а текст для користувача клієнт бере зі словника.
- Щоб додати мову: новий файл у `dictionaries/`, запис у `LOCALES`/`LOCALE_INFO` і в `DICTIONARIES` (`index.ts`).

## Цілі якості

- **Стабільність:** розкид загального балу ≤ 10 пунктів, середнє SD ≤ 4, збіг рівнів ризику по бітах ≥ 70%.
- **Бенчмарк:** ≥ 80% еталонів у своєму діапазоні, ≥ 90% правильних пар «сильний вище за слабкий».
- **Ціна:** один аналіз коштує кілька центів. Реальну цифру показують `benchmark` і `analyze`.

## Еталони

`benchmarks/fixtures.json` зараз містить 8 **синтетичних** сценаріїв, які я написав для старту. Справжня калібровка вимагає реальних сценаріїв з відомим утриманням (`"source": "real"`): свої відео, відео знайомих креаторів або учасників waitlist. Результати прогонів зберігаються в `benchmarks/results/`.

## Історія і ліміти (тиждень 4)

Усе працює через Supabase і тільки з серверу (`src/lib/supabase.ts`): браузер не бачить жодного ключа.

- **Користувачі.** Реєстрації немає. Під час першої перевірки сервер створює анонімного користувача Supabase, сесія живе в cookie. Тому історія прив'язана до браузера: очищення даних сайту = нова «особа». Потім анонімний акаунт можна перетворити на постійний (email), не втративши історії.
- **Історія** (таблиця `checks`). Кожен аналіз зберігається разом зі сценарієм, а хуки й переписування дописуються в той самий рядок. RLS дозволяє читати й видаляти тільки свої рядки, пише лише сервер (secret key). Відкрита перевірка живе в URL (`/?check=<id>`), тому переживає перезавантаження і кнопку «назад». `/api/hooks` і `/api/rewrite` тепер приймають тільки `checkId`: сервер сам бере сценарій і аналіз з бази, тож моделям не можна підсунути довільний текст.
- **Ліміти** (таблиця `usage_events`, `src/lib/limits.ts`), за ковзні 24 години:

  | Що | За замовчуванням | Env |
  |---|---|---|
  | Перевірки на користувача | 10 | `HOOKCHECK_LIMIT_ANALYZE` |
  | Хуки на користувача | 10 | `HOOKCHECK_LIMIT_HOOKS` |
  | Переписування на користувача (Opus) | 5 | `HOOKCHECK_LIMIT_REWRITE` |
  | Перевірки з однієї мережі (IP) | 30 | `HOOKCHECK_LIMIT_ANALYZE_PER_IP` |
  | Загальні витрати на моделі | $25 | `HOOKCHECK_DAILY_BUDGET_USD` |

  Функція `reserve_usage` перевіряє всі ліміти й резервує слот в одній транзакції (advisory lock), тому паралельні запити не проскочать понад ліміт. Якщо виклик моделі впав, слот повертається; якщо вдався, записується реальна ціна (з неї рахується загальний бюджет). IP зберігається лише як солоний хеш. Ліміт на мережу існує, бо анонімний акаунт легко перестворити, очистивши cookie.

## Акаунти (вхід через пошту або Google)

- Гість, як і раніше, отримує анонімного користувача при першій перевірці. Вхід (кнопка «Увійти» в шапці або сторінка `/account`) створює або відкриває звичайний акаунт. Після входу `/auth/callback` переносить перевірки й лічильники анонімного користувача цього браузера в акаунт і видаляє анонімного користувача (`src/lib/auth.ts`, `mergeAnonymous`). Так історія не губиться ні для нового акаунта, ні для вже наявного з іншого пристрою, а вхід/вихід не обнуляє ліміти.
- **Пошта:** посилання для входу (PKCE). Відкривати його треба в тому самому браузері. Якщо треба, щоб працювало з будь-якого браузера, змініть шаблон Magic Link на `{{ .SiteURL }}/auth/confirm?token_hash={{ .TokenHash }}&type=email`, для цього вже є маршрут `/auth/confirm`.
- **Google:** `/api/auth/google` → екран згоди Google → `/auth/callback`.
- `/account`: профіль, використання за 24 години, історія, вихід, видалення акаунта (разом з усіма перевірками).
- Куди повертати після входу, задає параметр `next`, дозволені тільки шляхи цього сайту (`safeNext`).

## Оплата: тариф Pro через Paddle (тиждень 5)

Paddle обрано замість Stripe, бо Stripe не приймає платежі для бізнесу з України. Paddle продає від свого імені (merchant of record): сам рахує й сплачує податки в кожній країні покупця і виплачує гроші в Україну (банк або Payoneer).

- **Тарифи.** Free: 10 перевірок, 10 наборів хуків, 5 переписувань на 24 години. Pro: 100 / 100 / 40 (env `HOOKCHECK_PRO_LIMIT_*`). Для Pro не діє ліміт на мережу. Ліміти задає `PLAN_LIMITS` у `src/lib/limits.ts`, тариф визначає `planFor` у `src/lib/billing.ts`.
- **Оформлення.** Pro доступний лише користувачам з акаунтом (гостю спершу пропонуємо увійти): підписка на анонімного користувача зникла б разом з cookie. Сервер створює транзакцію з `custom_data.user_id` (`/api/billing/checkout`), браузер відкриває для неї вікно оплати Paddle.js поверх сайту. Після `checkout.completed` браузер викликає `/api/billing/sync`, і Pro вмикається одразу. Керування й скасування через портал клієнта Paddle.
- **Синхронізація.** Paddle є джерелом правди. Таблиця `subscriptions` оновлюється webhook-ом `/api/billing/webhook` (підпис `Paddle-Signature` перевіряється, кожна подія заново читає підписку з Paddle, тому повтори й порядок подій не важать), після оплати і при кожному відкритті `/account` (`?refresh=1`). Pro діє при статусах `active`, `trialing`, `past_due`.
- **Видалення акаунта** спершу скасовує підписку в Paddle, щоб видалений користувач більше не платив.
- Якщо таблиць оплати ще немає або база недоступна, `planFor` повертає Free, а не ламає запит.

Налаштування Paddle (спершу в sandbox: sandbox-vendors.paddle.com):

1. Виконайте `supabase/migrations/20260927000000_billing.sql` у SQL Editor.
2. **Developer tools → Authentication**: створіть API key (`PADDLE_API_KEY`) і client-side token (`PADDLE_CLIENT_TOKEN`) → `.env.local`.
3. `npm run paddle:setup -- --amount 9 --currency USD` створює продукт і ціну; виведений `PADDLE_PRO_PRICE_ID` → `.env.local`.
4. **Checkout → Checkout settings → Default payment link**: адреса сайту (для локальної роботи в sandbox `http://localhost:3000/pricing`). Без неї Paddle не створює транзакції.
5. Webhook (**Developer tools → Notifications → New destination**): URL `https://<домен>/api/billing/webhook`, події `subscription.*` і `transaction.completed`, секрет → `PADDLE_WEBHOOK_SECRET`. Локально Paddle не достукається до localhost; оформлення і скасування все одно підтягуються (після оплати й на `/account`), але поновлення й невдалі платежі в реальному часі потребують webhook.
6. Тестова картка sandbox: `4242 4242 4242 4242`, будь-яка майбутня дата, CVC `100`.
7. Для живих платежів Paddle перевіряє сайт і бізнес (домен, сторінки з цінами, умовами, політикою повернення).
